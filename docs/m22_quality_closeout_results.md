# M22: bounded RULER quality closeout

Status: complete. All 13 arms and the independent artifact audit finished.
No additional 64K performance run is part of M22. This is the final planned
experiment; the user requested publication to GitHub main and project closeout.

## Why this replaces the old five-case quality headline

A hand-written five-case needle screen is useful for finding failures, not for
estimating general quality. M22 uses an existing open-source benchmark's data
generation and scoring rather than inventing another quality metric. It asks
two separate questions: how sparse inference performs relative to dense on
matched tasks that fit this GPU, and whether the M21 systems-only optimization
changes the sparse path's answers.

## Fixed protocol and provenance

- NVIDIA/RULER commit: `c3f5e3b4f87f97e048793bb510a3a6b19a46bf3a`.
- Data are generated by that commit's unmodified `scripts/data/prepare.py`
  and task generators with seed 42, the local Qwen3-4B Hugging Face tokenizer,
  and its `base` completion template including the official answer prefix.
  These are new generated inputs, not the previous community/Llama-2-sized
  files. No chat template is inserted into these legacy rows; the adapter's
  thinking-mode option does not change legacy completion prompts.
- Model: Qwen3-4B BF16 snapshot
  `1cfa9a7208912126459214e8b04321603b3df60c`, YaRN factor 4,
  RTX 3080 Laptop 16 GiB, WSL `NanoVLLM-Ubuntu`, TP=1/eager, eight CPU threads.
- Sparse baseline and M21 use the same fixed prefill/decode Top-32,
  64-token blocks, `r=4`, sink 64, recent 512, 4096-token prefill chunks,
  one mean-Q summary, FlashAttention backend and direct pinned gather.
  Only M21 enables `sparse_selector_static_mask`. Adaptive K, selector CUDA
  graph, K/V copy pipeline and finite-check profiling are off.
- 8K: 20 samples each of `niah_single_1`, `niah_multikey_2` and `vt`, each
  evaluated with dense, sparse baseline and M21. 32K: 10 samples each of
  `niah_single_1` and `niah_multikey_2`, with sparse baseline and M21.
  That is 80 distinct prompts and 220 prompt/arm generations across 13 arms.
- Greedy decoding, `ignore_eos=False`, the official NIAH generation cap of
  128 tokens and VT cap of 30. No post-hoc answer shortening or sample removal.
  Nominal context sizes include the generation allowance; actual prompt
  token lengths are recorded per sample and are not exactly 8192/32768.
- 32K dense is not run. The historical 32K dense attempt failed at the
  scheduler/block-allocation gate, before model forward, under its recorded
  batching and KV allocation budget. M22 does not retune the dense memory or
  batching configuration. This does **not** prove that every possible 16 GiB
  configuration is incapable of 32K dense inference. There are no dense-paired
  32K quality conclusions or 64K/128K quality results in this closeout.

`niah_single_1` asks for one hidden seven-digit value in repeated noise.
`niah_multikey_2` asks for a specified key's value among many similar-key
distractor needles: it is still a **single-reference** task, not a multi-answer
test. `vt` tracks a four-hop assignment chain and expects five variable names.
These three selected tasks do not cover all RULER task families.

## Scoring, exactly bounded

The driver imports NVIDIA's unmodified
[`scripts/eval/synthetic/constants.py`](https://github.com/NVIDIA/RULER/blob/c3f5e3b4f87f97e048793bb510a3a6b19a46bf3a/scripts/eval/synthetic/constants.py)
and extracts the pinned evaluator's `postprocess_pred` function without
importing its NeMo dependencies. That function strips text, replaces control
characters with newlines, and strips again.

For the selected tasks, the official `string_match_all` score is the mean
fraction of reference strings present in each prediction, case-insensitive,
multiplied by 100. For single-reference NIAH it is the percentage of samples
whose answer appears. For VT it is reference-item recall, **not** the
percentage of fully solved chains or exact-answer formatting accuracy.

Substring matching can reward an answer inside a verbose or partially wrong
response. M22 therefore publishes predictions and references for inspection,
records token-cap hits, and separately compares sparse/M21 token IDs. It does
not replace NVIDIA's metric with a custom scoring rule.

This is a **bounded RULER-derived regression screen**, not a full official
leaderboard run: only three selected tasks, 20/10 samples, one seed, legacy
completion templates and a custom NanoKV inference adapter. The current
[RULER repository](https://github.com/NVIDIA/RULER) directs full evaluations to
newer NeMo-Skills pipelines; those pipelines are not claimed here.

## Results

All scores below use the pinned official reference-matching metric (percent).

| Nominal context | Task | Samples | Dense score | Sparse baseline | M21 static mask |
| --- | --- | ---: | ---: | ---: | ---: |
| 8K | Single target in noise (`niah_single_1`) | 20 | 100 | 100 | 100 |
| 8K | Queried key among distractor needles (`niah_multikey_2`) | 20 | 100 | 80 | 80 |
| 8K | Four-hop variable tracking (`vt`) | 20 | 97 | 92 | 92 |
| 32K | Single target in noise (`niah_single_1`) | 10 | not run | 100 | 100 |
| 32K | Queried key among distractor needles (`niah_multikey_2`) | 10 | not run | 0 | 0 |

Sparse baseline and M21 have identical generated token IDs **and** raw answer
text on **80/80** matched prompts, and identical per-sample scores. This is
evidence of no observed answer change from the M21 static-mask optimization
on this screen; it is not evidence that sparse attention equals dense.

Actual engine input-token ranges are 8043–8055 (8K single), 7994–8051
(8K distractors), 8146–8160 (8K VT), 32619–32631 (32K single), and
32071–32635 (32K distractors). These ranges apply to the same prompts in
each matched arm.

The dense-paired 8K results detect a quality gap in the existing sparse
configuration, independently of the M21 systems optimization. The distractor
task missed four reference answers relative to dense (20 percentage points);
VT reference-item recall was five percentage points lower. The project must
not be described as lossless sparse attention or generally quality-preserving.

Sparse baseline distractor failures are sample rows 3, 6, 10 and 15 (one-based
row numbers in the public artifacts). Row 3 invents `4242424` rather than its
reference `1390292`; the other three initially claim the requested key is not
listed. Dense retrieves all four references. The cause is not isolated to
prefill routing, decode routing or a particular attention stage by this
evaluation, so no specific root cause or algorithmic repair is asserted.

The 32K distractor task misses all ten references in both sparse arms. Its
first responses commonly claim the target is not listed or invent a value.
Without a matched dense run at this length, this does not isolate model,
template, prefill-routing or decode-routing effects. It does establish that
the tested configuration is not reliable for this task. The failure is
retained, not repaired or removed during closeout. A successful 128K execution
demo must not be described as broad 128K quality validation.

For VT, all five reference variables are matched in 17/20 dense answers and
16/20 answers in each sparse arm; the official item-recall scores remain
97/92/92. This illustrates why the item-recall percentage is not the percentage
of completely solved chains. All **220/220** generations returned the task's
maximum token count. The cap-hit flag records this observation, not a distinct
EOS stopping reason, and no claim about unrestricted generation is made.

These results must not be compared numerically with the old hand-written
five-case screen: task inputs, context sizing and generation protocol differ.
They establish the new protocol's outcomes, not retrospective validation of
previous broad quality claims or a measured effective context length.

## Final verification

- Recomputed the official aggregate and per-sample scores from all published
  predictions; all match the scored JSON and final summary.
- Reloaded the pinned tokenizer on CPU, decoded all 220 token-ID sequences
  and checked exact equality with raw prediction text and original JSONLs.
- Re-encoded every prompt, checked actual input lengths and hashes, verified
  that reference strings occur in the generated task input, and checked
  prediction/sidecar path bindings and file hashes.
- Checked common recorded core-source hashes across all 13 arms and against
  the current files; the NanoKV runtime is unchanged during M22.
- Verified the nine recorded NVIDIA generation/evaluation files against the
  local pinned archive. Archive SHA-256:
  `3d6dd03fc79a145cc05dd1219164535e4618af8b2ad5b325083256254c28acab`.
- After all model jobs ended, the M14/M16/M17/M19/M20/M21/M22 focused
  regression selection passed: **61 passed in 3.22 s**. Python compilation
  and `git diff --check` also passed. This is not a new full-repository run.

The independent audit did not run the model again or change any answer/score.
Its compact verification record is `audit.json` beside the public results.

## Artifacts and reproduction

Public compact artifacts are in
[`benchmarks/results/m22_quality/20261003-closeout/`](../benchmarks/results/m22_quality/20261003-closeout/):
input hashes and generator-source hashes (`inputs.json`), the frozen
experiment (`plan.json`), 13 scored arm JSONs, and `summary.json`. Each arm
retains reference answers, raw/scored predictions, prompt hashes and actual
token lengths, generated token IDs, cap-hit flags and source provenance.
Full prompt JSONLs and predictions remain locally under ignored
`bench_logs/m22_quality/`; the public compact records contain no full prompts.

The preliminary input-only plan is retained as `plan.prepare-only.json`.
The final plan adds the finalized runner source hash; sample hashes and
experimental settings are unchanged. It is not a second scored experiment.

The first dense and sparse-baseline arm were measured on `178d9d5` plus
the uncommitted adapter; later arms use the versioned evaluation tooling.
Per-arm metadata preserves this distinction, and the summary checks matching
adapter/core-file hashes. The entire `nanovllm/` tree is unchanged between
`178d9d5` and the evaluation-source checkpoint `b0d2b6e`.
The sparse runtime SHA-256 is
`7509be43c51eb0534b80ea8efefa939f5375dfdba0361536645af54d5a07e6ad`.

Use the authoritative WSL virtual environment. Optional generator dependencies
are pinned in `benchmarks/requirements-m22-quality.txt`; retain the existing
PyTorch/CUDA inference environment rather than replacing it. Download the
NVIDIA RULER archive at the exact commit above, extract it locally, and pass
the source root explicitly. NLTK requires `punkt` and `punkt_tab` resources.

```bash
cd /opt/nano-vllm
source .venv/bin/activate
export HF_HOME=/opt/models/.cache/huggingface
export NLTK_DATA=/opt/nano-vllm/bench_logs/m22_nltk_data
uv pip install --python .venv/bin/python -r benchmarks/requirements-m22-quality.txt
python -m nltk.downloader -d "$NLTK_DATA" punkt punkt_tab
python benchmarks/run_m22_quality_closeout.py \
  --ruler-root bench_logs/m16_ruler_data/RULER-c3f5e3b4f87f97e048793bb510a3a6b19a46bf3a \
  --work-dir bench_logs/m22_reproduction \
  --results-dir bench_logs/m22_reproduction_results \
  --run-id independent-reproduction
```

Using new directories avoids the upstream generator's row-count-only skip
rule. For the completed local run, `--run-id 20261003-closeout --skip-prepare`
validates/reuses its frozen artifacts instead of silently rerunning or
overwriting them. Reproduction commands are optional future support, not an
instruction to resume development after closeout.
